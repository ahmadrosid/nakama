## Why plugins exist

Skills and custom tools cover one piece of a feature. A plugin ships the whole feature: a dashboard page, agent tools, and the data they share — without changing Nakama itself.

## What you get

After a package is approved and your organization turns it on:

- Members open native plugin pages from **Control center → Installed plugins**, using the dashboard theme
- Assigned profiles can call the plugin's tools in chat
- Notes and other plugin records stay in that organization

The same note you create on the page is the one the agent reads. Another organization never sees it.

## How plugins work

A plugin goes through three gates before your team uses it. Each gate has an owner.

![A plugin comes from npm, the official catalog, or an agent draft. A platform admin reviews and installs it, an org admin enables it, and a platform admin connects it to profiles. Members then use its page and chat tools.](/diagrams/plugin-lifecycle.svg)

1. **Review and install.** A platform admin checks the package and installs it. Nothing runs yet. Official plugins skip the separate platform approval.
2. **Enable.** An org admin turns the plugin on for one organization. This creates that organization's plugin data and starts any background workers the plugin needs.
3. **Connect to profiles.** A platform admin gives plugin tools to profiles. A profile without the tools cannot call them.

When someone uses the plugin, the page and the chat both run the same plugin actions:

![A member on the plugin page, or a profile in chat, starts a plugin action. Nakama checks the organization, role, and assignment, then runs the action on the server. The action uses its organization data and can use the profile's assigned tools.](/diagrams/plugin-runtime.svg)

- Nakama checks the organization, the user's role, the profile assignment, and that the plugin is on before each action runs.
- An action can use only its own organization's data.
- An action can call other tools only through a profile, and only tools assigned to that profile.
- In chat, a profile first searches for plugin tools by name. This keeps the start of each chat small when a profile has many plugin tools.

## How to use them

**1. Install a package (platform admin).** Open **Control center → Agent tools → Plugins**, enter the public npm package name and exact version, choose **Preview package**, review what it declares, and install it. Installation stores the package. It does not run plugin code and does not turn the plugin on for any organization.

**2. Activate it in the organization (org admin).** Stay in **Control center → Agent tools → Plugins**, add the plugin to the active organization, then enable it. Enable is what creates the organization's data store and makes the page available.

**3. Assign capabilities (platform admin).** Use the existing profile skill and tool pickers. Plugin items show as owned by the plugin. Assign them the same way you assign other skills and tools.

**4. Use the page (members).** Open the plugin from **Control center → Installed plugins**.

**5. Update or remove (org admin).** Choose **Update** to move to a newer approved release. A platform admin also sees an **Update** tag on a plugin when the registry has a version nobody approved yet. Choosing **Update** there opens the same package review as the first install, then updates the plugin, so the package name is typed only once. An enabled plugin is switched off for the update and back on afterwards, so its tools are unavailable for a moment. To remove a plugin, uninstall it. Uninstall keeps the organization's plugin data until you confirm a separate delete.

## Create a plugin with an agent

Ask Super Nakama to create a plugin when your team needs a custom page or agent
tool. Any other agent can do the same once an admin assigns it the
`create-plugin` skill (see [Skills](/skills)), so the agent already doing the
work can change the plugin it needs. An agent without the skill cannot submit a
draft. The agent starts from a template, prepares source files and built output,
and shows a plugin card in the chat. The draft stays uninstalled.

### What to ask for

A clear request gives a draft that needs fewer changes. Tell the agent:

- **What it does.** One sentence for each action, with the inputs it needs.
- **Who can run it.** Every member, or admins only.
- **Whether it changes data.** Say if an action saves, sends, or deletes something.
- **The page.** What people see and which buttons they use. Skip this if you only need an agent tool.
- **Agent use.** Say if profiles should call the action as a tool in chat.

For example:

> Create a plugin called Standup Notes. Add an action `add_note` that saves a
> note with a team name and text, for every member. Add an action
> `list_notes` that returns today's notes for a team. Show a page with a team
> picker, a text box, a Save button, and today's notes. Let profiles use
> `list_notes` as a tool.

To change a plugin, ask an agent with the skill, for example "add a delete
button to each note". It edits its own draft, or first copies the installed
release when another agent built the plugin or changed it since. It rebuilds,
then shows a new card. Review and install from the new card.

The card walks through five steps: **Drafted**, **Review and install**,
**Enable**, **Connect to profiles**, and **Try it**. Each step shows its button
only to the people who can do it, and the card updates as each step finishes.

1. As a platform admin, choose **Review and install** on the card.
2. Open the listed files to review the source, built code, and migrations. Code that runs is listed first.
3. Choose **Confirm installation**.
4. As an org admin, choose **Enable plugin**.
5. As a platform admin, choose **Choose profiles** and select the profiles that get its tools.
6. Ask one of those profiles to run the tool.

You can also review a draft from **System → Plugins → Install from folder**:
select the agent that built the draft, enter the draft ID, and choose **Preview draft**.

First installation stays disabled. First enable runs migrations and starts
workers. Reinstall resumes a previously enabled plugin after a successful
update. If migration fails, the plugin stays disabled with its previous data.
Changes to reviewed files require another preview.

Only platform admins can review or install local drafts. Plugin code has full
host access. Approve only code you trust. The agent needs an assigned shell tool
and Bun on the server to build; it reports missing prerequisites.

## Supermemory

Use Supermemory for the agent memory, shared organization memory, and knowledge base you already use in Nakama. Your existing memory tools, approval flow, and knowledge uploads stay in place.

1. An org admin opens **Control center → Agent tools → Plugins → Official plugins → Supermemory → Install**.
2. Enable the plugin. Nakama automatically uses your default OpenAI provider, or the first saved OpenAI provider if your default uses another service. If you use a separately managed server, open **Supermemory → Settings**, save its URL and API token, and use **Check saved connection**.
3. Keep using your agent's memory and knowledge base. Existing content moves to Supermemory when it is next read or searched; new knowledge uploads also sync automatically. Shared organization facts still require the usual approval before they are saved.
4. Ask your agent to search its knowledge base using everyday language. Explicit regular-expression searches still use the local extracted text.

The managed worker automatically reuses a saved OpenAI provider’s API key, URL, and default model for extraction, with local embeddings. Add an OpenAI provider in **Control center → Agent tools → AI Providers** if none is available. ChatGPT subscription connections are not supported by this worker. Restart Supermemory in **Control center → Workspace → Workers** after adding or changing your OpenAI provider. A changed provider configuration reindexes existing content on its next access, including failed documents. Verification makes a small API request; extraction and search also require the configured provider.

Nakama keeps local copies for recovery. Disabling the plugin returns your existing tools to those copies. Before the managed worker first becomes ready, memory stays local. After migration starts, an unavailable backend reports an error; restart the worker or disable the plugin to continue locally. Search can ask you to retry while new content is indexing.

The plugin's separate **Memory** and **Knowledge** collections remain available for previously saved items and explicit plugin actions. They are separate from the built-in memory and knowledge base. Installing the plugin does not automatically capture every conversation.

Documents show their processing state. Use **Check status** for an unresolved save and retry the same submission when asked. **Removal pending** means the item is excluded from plugin searches, but remote removal still needs retry. **Forget** is a soft deletion upstream, not permanent erasure.

Knowledge documents are sent as complete extracted text. Supermemory chooses their search chunks and uses its SuperRAG mode, which skips personal-memory extraction. PDF text extraction stays local; this setup does not require a separate Gemini account. Existing documents are reindexed on their next access after upgrading.

For built-in memory, replaced or removed versions stop appearing in search immediately. If Supermemory is still processing them, Nakama retries remote cleanup on later memory operations.

Use a dedicated Supermemory server per organization. Once content has been saved, the plugin keeps that server address fixed; an admin can still rotate its token. Disabling or uninstalling retains the external data. Back up the Supermemory server separately: Nakama's backup contains the connection and tracking records, not the external dataset. Restore into the same organization to retain access; moving records to a different organization requires fresh ingestion.

## Who can do what

| Action | Who |
|---|---|
| Install or remove a package | Platform admin |
| Enable, disable, update, uninstall, delete retained data | Org admin |
| Open plugin pages and call plugin actions | Members and admins |

## Trust

An installed plugin is trusted code. Approving a package lets that code run with the signed-in user's dashboard session and the server process. Organization folders keep one org's notes away from another org by accident. They do not protect you from a malicious plugin author.

## Backup

Plugin data is included in a full **Control center → Workspace → Settings → Export ZIP** backup as a consistent snapshot. Restore leaves plugins disabled until an admin enables them again. If a restored package no longer matches its stored hash, that release stays unavailable.

See [Backup and restore](/backup-restore).
