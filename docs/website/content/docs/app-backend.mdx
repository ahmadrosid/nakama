Use any app frontend with Nakama as the AI agent backend. Keep the Nakama API key in a server-side function or backend route, never in browser JavaScript.

## What you need

1. A reachable Nakama instance with an LLM provider and an organization default profile configured. Use HTTPS when Nakama is reached over a network.
2. An organization backend API key.
3. An app with a server-side function or backend route.

From the Nakama dashboard, open **Organization → Backend API keys**, enter a descriptive name such as `My app production`, and select **Create key**. Copy the secret immediately; it is shown only once.

Use the key name to identify its use, for example `My app production`, `My app staging`, or `My app preview`. Create separate keys when you want to revoke one environment without affecting another.

You can also create a key from an authenticated admin environment:

```bash
curl -X POST "$NAKAMA_URL/v1/orgs/$NAKAMA_ORG_ID/api-keys" \
  -H "Authorization: Bearer $NAKAMA_ADMIN_TOKEN" \
  -H "X-Org-Id: $NAKAMA_ORG_ID" \
  -H "Content-Type: application/json" \
  -d '{"name":"My app production"}'
```

Save the returned `secret` as a server-side secret named `NAKAMA_API_KEY`. Also save `NAKAMA_URL`. The API key identifies the Nakama organization, and Nakama uses that organization's default profile. The secret is returned only once; rotate it if it is exposed.

## Minimal server flow

Your app backend calls Nakama in two steps. Create a session once:

```ts
const session = await fetch(`${process.env.NAKAMA_URL}/v1/sessions`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.NAKAMA_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    channel: "web",
    appUserId: authenticatedUser.id,
  }),
});

if (!session.ok) {
  throw new Error(`Could not create Nakama session (${session.status})`);
}
const { sessionId } = await session.json();
```

Then send each message with that `sessionId`:

```ts
const reply = await fetch(
  `${process.env.NAKAMA_URL}/v1/sessions/${sessionId}/messages`,
  {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.NAKAMA_API_KEY}`,
      "X-Nakama-App-User-Id": authenticatedUser.id,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ message: userMessage }),
  }
);

if (!reply.ok) {
  throw new Error(`Nakama message failed (${reply.status})`);
}
const { reply: answer } = await reply.json();
```

The non-streaming response is JSON:

```json
{
  "reply": "Hello! How can I help?",
  "contextUsage": {
    "breakdown": {
      "conversation": 420,
      "systemPrompt": 980,
      "toolDefinitions": 310
    },
    "contextWindow": 128000,
    "source": "estimate",
    "usableContextTokens": 120000,
    "usedTokens": 1710
  }
}
```

`contextUsage` is optional. Use `reply` as the assistant message and ignore `contextUsage` unless you want to display context or token information.

For streaming replies, send `{"message":"...","stream":true}`. Nakama returns Server-Sent Events. Each event is one JSON object on a `data:` line:

```text
data: {"type":"chunk","delta":"Hello"}

data: {"type":"chunk","delta":"!"}

data: {"type":"done","reply":"Hello!","contextUsage":{"contextWindow":128000,"source":"estimate","usableContextTokens":120000,"usedTokens":1710}}

```

Append each `chunk.delta` to the assistant message. Stop on `done`; show `error.error` if an `error` event arrives. Other events can report `thinking`, tool activity, todos, questions, or usage. Proxy the SSE response through your backend to the browser.

Tool activity uses these events:

```text
data: {"type":"tool_start","toolCallId":"call_1","tool":"search_files","input":{"query":"pricing"}}

data: {"type":"tool_end","toolCallId":"call_1","tool":"search_files","result":{"matches":[]}}
```

Other event examples:

```text
data: {"type":"thinking","delta":"Checking the available files..."}

data: {"type":"usage","usage":{"inputTokens":1200,"outputTokens":80,"totalTokens":1280}}

data: {"type":"todos_updated","todos":[{"id":"todo_1","content":"Check pricing files","status":"completed"}]}

data: {"type":"questionnaire_updated","questionnaire":{"id":"question_1","title":"Need more details","questions":[]}}
```

Render tool activity or thinking as optional progress UI. Most clients only need to handle `chunk`, `done`, and `error`.

## App-user workspace and storage

Nakama creates the private workspace when an app user starts their first API-key session. It does not create a Nakama organization user.

The initial workspace creates empty `memory-archive` and `artifacts` directories. The profile's soul, style, and instructions are shared and read live, so they are not copied for each user. The initial logical file content is effectively **0 KB per user**; practical disk usage is usually only a few KB for directory entries. For 1,000 users, plan for roughly **a few MB** before memory, uploads, and artifacts are added.

Memory, archived memories, uploaded files, and saved artifacts grow beyond this baseline. The workspace is created on first session use, not when an app user record is created.

Assigned skills are shared profile capabilities. Their user-created files stay in the app user's private workspace, but public API users cannot change the profile's shared skill configuration.

## Security checklist

- Never use `NAKAMA_API_KEY` in a React component or browser fetch.
- Never commit the key or include it in a client-visible response.
- Use separate named keys for production and preview deployments where possible.
- Revoke or rotate a key when a project is duplicated, shared, or compromised.
- Keep `appUserId` from your server-side auth session; never trust it from the browser.
- Keep `appUserId` stable for the same person so Nakama can return that person's workspace.
